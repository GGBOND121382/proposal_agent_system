# 调研报告内容 MVP：后续工作清单

日期：2026-09-12。

本文是后续实施清单，不表示功能已经实现。用户最新要求优先于前序文档中更完整、更重的流程设计。

## 1. 用户目标与本轮边界

首要目标：基于现有任务材料和 WF-3B 研究产物，生成一份结构完整、事实有依据、能够阅读和导出的调研分析报告。

用户明确要求：

- 保留提纲整理，不能直接把固定章节标题交给模型盲目扩写。
- 保留影响内容正确性的检查。
- 安全、隐私等类型的报错，如果不影响文档正确性，不要阻断内容生成。
- 第一阶段先实现内容完整、正确，再完善复杂治理、审计和高级交付能力。

适用范围：手动指定 `document_type=SURVEY_REPORT` 的报告分支。不要全局关闭申请书分支或其他任务的校验。

当前案例：项目 `project-d39c11d09c7445d3`，题目《美空军DASH系统调研分析报告》。WF-1、WF-3B 已有完成实例；具体版本应绑定实际选定的前置流程，不隐式读取“项目最新值”。

当前已核实的实现边界：报告 WF-4 的冻结步骤只有 `P-REPORT-OUTLINE` 和 `P-REPORT-OUTLINE-CRITIC`；正文生成、整合与交付尚未加入这条报告路径。最新已审计阻断是模型连接错误，不能靠放宽内容校验解决。

## 2. MVP 的最短合理流程

```text
读取并冻结任务要求、研究版本
  → 整理提纲与证据分配
  → 一次提纲检查，必要时一次针对性修订
  → 分章生成正文，每章立即保存
  → 全文内容检查，必要时一次针对性修订
  → 生成摘要、结论并检查与正文一致
  → 保存完整 Markdown；支持时同时导出 DOCX
```

可以复用已有模型节点和存储能力。不以新增通用框架、完整知识图谱或大量状态对象为前提。

安全、隐私等外围检查可记录告警后继续内容流程；内容错误按影响范围修正，不因一章失败丢弃其余章节。

## 3. 第一优先级：接通提纲到正文

### M0. 确认实际执行入口与模型连接

- [ ] 确认实际运行的服务已加载当前代码，避免修改文件后仍验证旧进程。
- [ ] 在服务实际环境中检查模型接口可调用；DNS 解析成功不等于完整调用成功。
- [ ] 区分连接/超时错误与模型输出错误，使用有限重试，不把连接错误路由成语义修复。
- [ ] 在界面和日志中显示实际 provider 模型名称、失败节点与具体原因。

验收：能取得一次真实模型响应，或准确报告服务连接不可用；不能声称连接失败已通过关闭审查解决。

### M1. 冻结报告任务和资料版本

- [ ] 读取用户指定的报告类型，不再根据“任务书”“指南”等字样重新分类。
- [ ] 冻结选定的 WF-1、WF-3B 及其研究产物版本。
- [ ] 保留题目、必答问题、技术深度、资料截止日期、结构、篇幅建议和未知处理原则。
- [ ] 直接使用已有材料中的明确要求，不反复向用户确认。
- [ ] 不运行无必要的 WF-2；只有用户指定参考模板时才纳入。

验收：实际提纲请求包含完整任务要求与正确研究版本，后续章节使用同一版本。

### M2. 保留并接通提纲整理

- [ ] 以用户结构为起点，根据实际证据调整章节顺序、粒度和合并关系。
- [ ] 每章明确：标题、要回答的问题、已有证据、缺口、预计篇幅、必要图表。
- [ ] 区分“模块做什么”“流程如何衔接”“技术为何能起作用”，减少跨章重复。
- [ ] 为实验轮次、演进、技术路线和效果比较安排明确位置。
- [ ] 提纲基于证据可得性安排内容，不把所有未知项扩展成空泛章节。
- [ ] 模型只输出提纲业务内容；正式 ID、版本、来源元数据和统计由代码生成。
- [ ] 若节点声称使用 Semantic Schema，实际注册、模型输入输出契约及装配必须一致。

验收：获得可供逐章写作的提纲，而不仅是几个章节标题。

### M3. 一次轻量提纲检查

- [ ] 保留一次提纲检查，重点是必答问题遗漏、结构重复、证据错配、内容超范围和申请书化。
- [ ] 轻微表达和排版问题转成正文写作提示，不阻断。
- [ ] 资料不足但可明确呈现缺口的章节允许进入写作。
- [ ] 发现实质问题时，最多进行一次针对性提纲修订；输入原提纲和具体问题，避免无上下文整体重生成。
- [ ] 修订后仍有问题时列出具体未解决项，并继续不受影响的章节；不能无限返回提纲阶段。

验收：提纲不会因风格偏好或外围检查陷入循环；报告主题和必答问题仍受到检查。

### M4. 实现真正的分章正文生成

- [ ] 将正文生成加入报告 WF-4，而不是在提纲审查结束后就将完整写作任务标记为完成。
- [ ] 每次处理一章，输入该章要求、相关证据卡、归档正文摘录、来源编号及明确缺口。
- [ ] 不能仅依靠少量综合卡片扩写长报告；技术解释应有相关正文支撑。
- [ ] 为跨章节一致性提供简短术语表和已完成章节摘要，不反复传全量历史。
- [ ] 正文可以直接采用 Markdown，或使用很小的业务契约承载正文及引用；不让模型生成大批数据库和审计字段。
- [ ] 每章生成后立即保存正文、来源绑定和所用输入版本。
- [ ] 单章失败只重试该章，已经完成的章节可查看、下载并复用。

验收：真实产生各章正文并落盘/持久化。只有提纲、写作计划或状态 PASS 不算通过。

## 4. 第二优先级：保证内容完整与正确

### M5. 明确调研报告/综述的写作要求

- [ ] 围绕对象展开定义、演进、模块、架构、流程、技术和效果，不以宏观 AI 背景替代。
- [ ] 不只是逐篇资料摘要；需要比较不同来源、实验轮次和技术描述，形成有依据的综合解释。
- [ ] 清楚区分官方披露、厂商自述、来源转述、通用原理和作者分析。
- [ ] 无直接证据时不认定 DASH 使用特定模型、RAG、知识图谱、强化学习或具体框架。
- [ ] 数值结论保留指标定义、单位、场景、基线、时间和适用范围。
- [ ] “本次未取得证据”不能写成“官方从未披露”；抓取失败不能当作技术未公开的证明。
- [ ] 资料不足时完整回答“目前能确认什么、不能确认什么、为什么”，而不是补造细节。

这里的“内容完整”是必答问题均有回应，包括有依据的未知说明；不是要求所有技术细节都必须有确定答案。

### M6. 先完成必要表格，复杂图示按需做

- [ ] 模块/功能表：名称、用途、输入输出、上下游、人员位置、实验轮次、证据及未知项。
- [ ] 技术表：解决的问题、机制、对应功能/流程、公开实现证据、局限。
- [ ] 效果表：轮次、场景、比较基线、指标、公开结果、证据属性、适用边界。
- [ ] 来源与观点比较表：存在冲突或差异时列出各方描述与采信依据。
- [ ] 架构图和流程图只有在有助于解释且有依据时生成；渲染失败先保留文字说明或表格，不阻断全文。
- [ ] 分析性架构和官方架构必须清楚区分。

### M7. 一次全文内容检查与有限修订

- [ ] 检查所有必答问题是否被正文或明确缺口回应。
- [ ] 检查来源是否支持关键结论，不能只检查引用 ID 存在。
- [ ] 检查事实、数值、术语、时间线前后是否一致。
- [ ] 检查跨章重复、明显遗漏和无依据的结论升级。
- [ ] 只修订受影响段落/章节，不重新生成已正确的全文。
- [ ] 全文自动修订默认最多一轮；未解决的事实问题明确标注，不伪装成“已确认”。
- [ ] 内容检查不能要求我方团队基础、创新链、经费、研发实验等申请书专属内容。

### M8. 摘要、结论与整合

- [ ] 摘要和最终结论在主体正文形成后生成，避免提前写出没有证据支撑的结论。
- [ ] 摘要、正文和结论使用相同的事实范围与不确定性表述。
- [ ] 代码负责章节拼接、目录、顺序、引用编号和重复文献合并。
- [ ] 全文检查后如果主体发生实质修订，同步调整摘要与结论。

## 5. 错误处理：哪些继续，哪些必须修正

必须按错误实际影响分类，不仅根据节点名称或 Finding 前缀决定。不能把来源损坏包装成“隐私问题”后直接忽略。

| 问题 | MVP 行为 | 是否阻止保存已有正文 |
|---|---|---|
| 安全/隐私分类器异常、外围审查超时，且不影响内容正确性 | 记录告警与未完成检查，继续生成 | 否 |
| 不适用的申请书安全/合规字段或形式要求 | 对报告分支跳过，保留适用范围记录 | 否 |
| 隐私处理破坏了关键事实、来源或正文 | 恢复正确输入或修正受影响内容，不能以隐私告警为由忽略数据损坏 | 否；受影响内容不能当作已核验结论 |
| 模型接口连接失败/超时 | 有界重试；保存进度，支持续跑 | 否 |
| 提纲轻微风格问题 | 作为写作提示，继续 | 否 |
| 图示渲染、格式美化失败 | 降级为文字/表格或延后处理 | 否 |
| 不影响正文的审计回执、额外统计缺失 | 记录待补，继续 | 否 |
| 未设定的可空协议字段缺失 | 代码按明确规则补 null/空集合，不能编造业务约束 | 否 |
| 关键事实错误、无依据数字、引用支持关系错误 | 修正、删去错误断言或明确标为待核对；修正前不能宣称内容正确 | 否；可以保存工作稿 |
| 必答问题完全遗漏 | 补充章节/段落或明确资料缺口 | 否；不标记内容完成 |
| 引用目录丢失、跨版本资料混用 | 修复映射/版本，不能把无法溯源的结论当已核验内容 | 否 |
| 输出无法解析、关键章节为空 | 局部恢复/重试，不能用 PASS 或空对象占位完成 | 否 |

“不阻断”是继续生产和保存内容，不是自动给安全审查、隐私审查或事实检查写入 PASS。未运行、失败、跳过应如实区分。

本地报告内容生成、已有对外传输动作和正式发布是不同操作。外围检查降级不应顺带扩大外发范围、修改安全等级或新增外部接收方；本 MVP 不需要做这些改动。

## 6. 非阻断机制的最小实现要求

- [ ] 在 SURVEY_REPORT 的内容 MVP 模式下启用明确策略；原工作流默认行为不整体改变。
- [ ] 使用可复核的非阻断问题清单，并记录原因、节点和影响范围。
- [ ] 业务正文、恢复点与告警分别保存，避免告警处理异常导致正文丢失。
- [ ] 不把外围检查失败送入重复的模型内容修复链。
- [ ] 不通过直接改数据库状态来绕过真实未完成的正文工作。
- [ ] 每次结束都能向用户展示：已有内容、未完成章节、内容待修项、被跳过的外围检查。

命名可以复用现有配置和状态，不要求为此创建新的复杂状态机。

## 7. 第三优先级：可查看、可恢复、可交付

### M9. 先保证完整 Markdown 交付

- [ ] 持久化一份连续、可阅读的 Markdown 全文，不只散落在模型调用日志里。
- [ ] 用户可以下载全文，也可以查看已完成章节。
- [ ] 包含正文、必要表格、参考资料、术语及证据缺口说明。
- [ ] DOCX 导出可复用现有能力；如只剩格式或渲染问题，不影响 Markdown 内容交付。
- [ ] 报告标题、文件名和章节内容使用调研报告表述。

### M10. 分清内容完成与外围检查状态

- [ ] “提纲完成”不显示为“报告完成”。
- [ ] “正文部分完成”明确列出缺失章节。
- [ ] “内容完成但外围检查未执行”允许交付内容成果，并如实显示检查状态。
- [ ] 仍有关键事实待核对时标为工作稿，不能同时宣称内容已正确验收。

可以使用现有 artifact 元数据表达这些状态，避免为 MVP 重构所有 workflow status 枚举。

## 8. 代码接续位置与改动顺序

1. `app/workflow_defs.py::WF4_REPORT_BRANCH_STEPS`：补齐报告正文、整合路径；检查已经冻结的旧实例如何续接或重建，不能改列表后假设老实例自动变更。
2. `prompt_pack/prompts/report/` 及对应注册/Schema：先保证提纲业务契约一致，再补小型分章写作与内容检查契约。
3. `app/context_base.py`：按章节提供冻结的研究卡片、正文摘录、来源与缺口。
4. 实际使用的 `app/workflows.py`、写作执行器与运行时：章节持久化、失败续跑、外围问题非阻断策略。
5. 现有 Guard/审查模块：只保留报告内容相关判断作为内容验收条件；不适用的科研申请书要求跳过。
6. 导出和页面：全文可见、可下载，展示内容状态与检查状态。

先检查实际调用入口和已有改动，不重复建设同类模块。不要为了图形界面、完整审计或新框架而推迟正文生成。

## 9. 验收清单

### 自动化/隔离验证

- [ ] 提纲检查告警不会阻止正文开始；实质性漏项会形成明确修订任务。
- [ ] 一个外围安全/隐私检查失败后，报告仍继续生成，且记录真实失败状态。
- [ ] 注入事实错误、错误数字、错误来源时，系统不会把它当成已核验内容。
- [ ] 单章生成失败不删除已完成章节，重试不重复覆盖无关章节。
- [ ] 图形渲染失败仍可导出 Markdown 全文。
- [ ] 已有提纲和卡片编号能解析，来源映射没有跨 run/版本混用。
- [ ] 报告分支的降级不影响原申请书分支。

### 真实 MVP 验收

- [ ] 使用当前 DASH 项目的真实 WF-1、WF-3B 产物跑完，不使用模拟正文冒充。
- [ ] 输出整理过的提纲、各章正文、必要表格、摘要、结论和参考资料。
- [ ] 读者能找到模块、流程、技术、效果四项要求的实质回应；资料不足部分给出具体边界。
- [ ] 关键论断有可追溯依据，没有用通用技术常识冒充 DASH 实现。
- [ ] 生成并提供完整 Markdown 文件；记录 DOCX 是否同时完成。
- [ ] 报告中不存在我方研发方案、团队基础或创新成果等任务外内容。
- [ ] 如有外围检查被跳过，用户仍能拿到内容成果，且没有虚假的检查通过记录。

## 10. 本轮暂缓事项

- 完整科研论证图、中心命题—创新—实验链。
- 多级独立审查、无限语义修复与自动仲裁。
- 通用跨任务编号系统重构。
- 复杂图示和出版级排版。
- 全流程安全/隐私治理体系重构。
- 与本报告无关的其他文种适配。

最终交付标准：**整理过的提纲 + 有依据的完整正文 + 可用的全文文件 + 明确的缺口和检查状态。** 仅有提纲通过、Schema 通过或流程状态 COMPLETED，均不算完成本 MVP。
