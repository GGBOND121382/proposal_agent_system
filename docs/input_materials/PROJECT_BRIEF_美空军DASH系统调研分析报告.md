# 输入任务书：美空军DASH系统调研分析报告

## 一、任务定位

请撰写《美空军DASH系统调研分析报告》。本任务属于公开资料调研与技术分析，交付物为中文调研报告。

核心目标是让读者能够理解：DASH是什么、由哪些功能和技术组成、如何运行、人和软件如何协同，以及公开试验能够证明它达到了什么效果。

背景调研必须深入到DASH本身的功能、软件架构、流程、技术与试验结果。不能用泛泛的人工智能发展、智能化战争趋势、国防AI市场规模或通用多智能体介绍替代。不得将本任务改写成“拟研制一个类似系统”的项目申请书，不得虚构我方团队基础、研发方案、经费或创新成果。

## 二、研究对象与范围

首先核验DASH的正式名称、组织归属、发展阶段及其与ABMS、C3BM等相关体系的关系。区分实验系列、实验环境、参试软件原型、集成架构与已部署能力，不能因报告题目使用“系统”就预设其已经形成单一、定型、正式列装的产品。

检索应覆盖DASH各轮公开实验，以及与其直接相关的后续集成验证。重点核查DASH 1、DASH 2、DASH 3与MASH的功能差别和演进关系。以2026年9月9日为本次资料截止日期，并分别记录事件时间与报道时间。

英文检索同时使用DASH及其全称Decision Advantage Sprint for Human-Machine Teaming，并结合Air Force、ABMS、AFRL、ShOC-N等上下文消歧；中文检索覆盖“美空军DASH”“人机协同决策优势冲刺”等表述。

## 三、背景调研必须回答的问题

### 1. 包含哪些模块或功能？

根据公开证据梳理功能组成与相互关系，重点核查：

- 公开决策功能，例如Perceive Actionable Entity、Match Effector、Generate Battle Courses of Action的职责及差异。
- 多厂商软件或微服务的编排、调用与集成。
- 数据、元数据、本体或共同语义的交换与管理。
- 人机交互、人员审核、建议解释与操作反馈。
- 仿真环境、过程记录、性能评估与人因测量。

这些是待核查方向，不是预先认定的实际模块清单。必须区分“官方明确命名的功能”“厂商明确披露的组件”和“作者为便于分析归纳的功能层”。

每个可确认的模块或功能均需说明：名称、用途、输入信息类别、输出结果类别、上下游关系、人员参与位置、对应实验轮次、证据来源和未知细节。至少形成一张模块/功能对照表及一张带来源说明的架构关系图。

### 2. 包含哪些流程？

分别说明两类流程：

- **软件与人员协同流程**：公开场景信息如何进入软件，相关功能怎样衔接，结果如何呈现给人员，人员如何审核或反馈，以及过程如何被记录与评估。只描述来源能够支持的功能级流程。
- **实验与迭代流程**：如何建立人工基线，如何引入软件辅助，如何组织对照试验、收集操作员反馈、修改原型并再次验证。

至少提供一张流程图或泳道图，标明人员、软件服务和评估环节的职责。不能把作者推测的逻辑顺序写成DASH已公开的固定执行协议；无法确认的接口、顺序和反馈机制应明确标注。

### 3. 涉及哪些专业技术？

围绕实际功能，核查以下技术方向是否有DASH直接证据：

- 决策功能建模与任务分解。
- 微服务、模块化架构、服务编排及多厂商互操作。
- 知识表示、本体、数据语义一致性与元数据交换。
- AI辅助推理、方案生成、搜索或优化及约束处理。
- 人机交互、人因工程、认知负荷、信任与可解释性。
- 仿真验证、对照实验、过程测量与效果评估。

每项技术按“解决的问题—作用机制—对应功能或流程—公开实现证据—局限”展开，不得仅罗列术语。

必须区分DASH已披露采用的技术、厂商自述、通用技术原理及作者推断。没有直接证据时，不得认定DASH采用了某种大语言模型、RAG、知识图谱、强化学习算法或具体开源框架。可解释相关原理，但必须标为背景知识。

### 4. 能达到什么效果？

按实验轮次和具体功能整理效果，重点考察决策耗时、有效方案或任务产出数量、结果质量、人员工作负荷、交互负担、互操作性及原型迭代效率。

每项效果结论须交代：试验场景、参与对象、人工或既有工具基线、辅助条件、指标定义、公开结果和适用范围。区分定量测量、官方定性结论、参与者体验和厂商宣传。

来源没有公布数值时，应写“未公布可核验数值”。不得自行补充准确率、时延、提升百分比或成熟度等级；不得把个别参与者体验换算成普遍性能，也不得把仿真结果直接外推为实战效果。

至少形成一张“实验轮次—验证功能—对照方式—效果证据—局限”表。

## 四、资料与检索要求

优先检索美空军、AFRL、ShOC-N/805th CTS等机构的原始发布、技术报告、论文和公开演示材料；厂商资料和中文分析用于补充，并注明来源属性。

先澄清研究对象，再按模块、流程、技术和效果分别检索。根据首轮来源中出现的正式术语、机构、软件名称和实验名称定向补查，避免始终使用宽泛的“军事AI”查询。

关键技术与效果结论应引用实际阅读的正文。搜索摘要只作为线索；同一报道的转载不能算作独立验证。若技术细节未公开，说明查到哪里、缺少什么，不能以通用原理补写成系统事实。

## 五、报告结构与验收要求

建议报告结构：

1. 摘要与主要发现。
2. 背景调研：研究对象、发展历程、功能组成、架构关系、运行与实验流程、关键技术、效果证据。
3. 综合分析：技术特点、成熟度、局限与公开证据缺口。
4. 结论。
5. 参考资料、术语表与证据对照表。

背景调研应占正文主要篇幅，建议约60%—70%；其内部以功能、流程、技术和效果为主。建议全文6000—10000字，按证据密度调整，不以扩充宏观背景凑字数。

验收时，读者应能从报告及图表中明确回答“有什么、怎么运行、用了什么技术、效果如何、哪些仍不知道”。所有关键事实可追溯，分析性架构与官方披露有清楚区分。材料不足时交付已证实内容和具体缺口，不得用推测制造完整性。
