# 调研分析报告的后续工作流适配说明

日期：2026-09-11。本文是实施方案；仅新增本文档，不代表下述功能已实现或验收。

## 1. 目标、现状与范围

用户要完成《美空军DASH系统调研分析报告》，重点解释对象本身的功能模块、架构、运行与实验流程、技术机制、公开效果及证据边界。不是设计我方类似系统，也不是撰写科研项目申请书。

项目已手动指定 `document_type=SURVEY_REPORT`。已核实 WF-1 `wf-b943ade032da44f7` 为 COMPLETED，完成时间为 2026-09-11 10:48 北京时间；项目 ID 为 `project-d39c11d09c7445d3`。

用户允许简化与跳过困难的非必要任务。因此分阶段实施：

1. 先适配 WF-3B 的技术调研维度，再运行检索、归档与综合。
2. 有研究产物后，适配 WF-4 的报告提纲、证据组织和正文写作。
3. 最后核对 WF-5 的报告审查与导出。

不在本任务中重构通用智能体框架、重写搜索引擎、扩展科研知识图谱或重新执行已完成的 WF-1。保留之前做好的手动文种、语义契约、中文检索、实体定向检索与两轮来源合并。

前序说明：

- `docs/WF1_MANUAL_DOCUMENT_TYPE_HANDOFF_20260910.md`
- `docs/WF1_REFERENCE_REPAIR_CHANGE_SPEC_20260911.md`

历史文档中的未完成状态可能已经变化；以本次实际代码和运行记录为准。

## 2. 路径选择：WF-2 不是检索前提

当前代码 `app/workflows.py::_required_workflow_types` 的实际依赖：

| 工作流 | 当前必须的前置流程 |
|---|---|
| WF-2_TEMPLATE_EXTRACTION | 此函数未设置流程前置；节点仍需可用参考材料 |
| WF-3_HYBRID_ONLINE_ASSIST | WF-1 |
| WF-3B_TOPIC_BACKGROUND_RESEARCH | WF-1 |
| WF-4_PROPOSAL_AUTHORING | WF-1 + WF-2；按配置可额外要求 WF-3 |
| WF-5_SECURITY_REVIEW_AND_EXPORT | WF-4 |

本报告建议路径：

```text
已完成 WF-1
  → 适配后的 WF-3B：技术调研、证据归档、综合与缺口
  → 适配后的 WF-4：报告提纲、分章写作、证据审查
  → WF-5：最终审查与报告导出
```

WF-2 只在用户有指定报告模板、参考报告或必须复用的版式时运行。如果没有参考模板，就使用任务材料明确给出的报告结构，暂不运行 WF-2。

但当前 WF-4 硬性要求 WF-2，必须修改报告分支的依赖与上下文组装，不能只在界面隐藏 WF-2、伪造其完成，或从 replay 补一个模板。

WF-3B 是否需要 WF-2 与 WF-4 是否需要 WF-2 是两件事：前者现在就不需要；后者需要做报告模式适配。

## 3. 全链路共享一个用户指定的文种

权威输入继续使用项目配置 `document_type=SURVEY_REPORT`，不再扫描“任务书”“指南”等字样重新分类。

工作流启动时将所用文种、研究维度版本、材料截止日期和前置工作流 ID 冻结到本次运行状态。后续节点读取该快照，避免项目配置在运行中变化后混用不同策略。

已有 canonical 合同把 SURVEY_REPORT 映射成 `TECHNICAL_REPORT`。这只是兼容映射，不能据此丢掉“本次是调研报告”的具体模式。建议保留独立的运行模式字段，不把现有合同枚举一次性全部重构。

以下概念分开：

- 用户选择的交付类型：调研报告。
- 上传文件角色：任务说明、参考模板、技术资料、证据材料等。
- 调研充分性：充分、部分覆盖或存在缺口。
- 工作流完成状态：协议执行是否结束。

WF-1 完成意味着任务受理完成，不代表已有技术结论；WF-3B 完成也不自动意味着所有技术问题都有答案。

## 4. 第一阶段：WF-3B 技术调研适配

### 4.1 当前不适配的地方

`app/background_research.py::BACKGROUND_DIMENSIONS` 固定八个应用背景维度：

APPLICATION_SCENARIO、STAKEHOLDER_AND_PAIN、INDUSTRY_SCALE_AND_TREND、POLICY_STANDARD_AND_PROGRAM、REPRESENTATIVE_CASE、CURRENT_ADOPTION、OPERATIONAL_CONSTRAINT、RESEARCH_SIGNIFICANCE。

`normalize_required_dimensions` 当前只允许这些维度；未指定时默认全部八项。模型也被要求不得生成冻结集合之外的维度。

因此，仅在 topic/focus 写“技术细节要详细”不能保证模块、接口、技术机制和实验效果得到独立覆盖。直接追加几个新枚举而不修改覆盖判定，同样不够。

### 4.2 最小实现：按报告模式选择维度配置

保留原八维配置，给 SURVEY_REPORT 增加一套技术调研配置。以下是建议名称，当前尚未实现，不能直接作为现有 API 参数使用：

| 建议维度 | 必须回答的内容 | 优先产出 |
|---|---|---|
| OBJECT_AND_EVOLUTION | 是什么、组织归属、发展阶段、各轮演进、与相关体系关系 | 定义与时间线 |
| FUNCTION_AND_ARCHITECTURE | 可证实的模块/功能、输入输出、上下游、接口、数据交换、人参与位置 | 模块表、架构图 |
| WORKFLOW_AND_INTERACTION | 软件运行流程、人机协同，以及实验反馈与迭代流程 | 流程图或泳道图 |
| TECHNOLOGY_AND_IMPLEMENTATION | 技术解决什么问题、如何起作用、在哪个功能使用、有何实现证据 | 技术—功能—证据表 |
| EVALUATION_AND_EFFECT | 实验场景、基线、指标定义、公开结果、适用范围 | 实验效果表 |
| LIMITATIONS_AND_GAPS | 未确认内容、披露边界、冲突、成熟度局限 | 证据缺口表 |

行业规模和研究意义不再是这类报告的强制必查项；可作为用户明确要求时的补充，不能挤占系统技术调研篇幅。

建议以一个配置解析函数提供允许维度及默认必需集合，各节点共享，避免在多个文件各维护一份列表。

必须同步：选项归一化、前端选择、模型/canonical Schema、计划与计划审查、搜索执行、覆盖统计、综合、研究审查及最终研究产物持久化。

特别检查代码中的 `or BACKGROUND_DIMENSIONS` 回退。已选择技术调研模式时，不能在某个后续函数又回到旧八维。

### 4.3 传入任务深度，不能只传标题

WF-3B 输入至少保留：

- 用户指定的类型和 topic。
- 原任务的必答问题、重点维度和证据要求。
- 资料截止时间、来源优先级、范围与排除项。
- 图表与报告交付要求。

当前材料截止为 2026-09-09，不能因当天系统日期变化自动修改。各轮 DASH/MASH 的名称、正式全称、组织和体系关系仍需核验，不能在计划中把待证内容当成事实。

已明确的报告结构、公开资料边界和未知标注原则直接执行，不反复问用户确认。

### 4.4 查询规划与补查

继续复用已有实体核验、简短单问题查询、原始语言查询、中文补充查询、首轮来源驱动补查等机制。

把“要查哪些问题”分配给六个维度，避免仅用“军事 AI”“人机协同决策”检索宏观背景。模块、流程、技术和效果查询应绑定 DASH 或已核实的直接相关对象。

按来源类型区分证据用途：官方发布用于事件与公开结论；公开技术报告、论文与演示材料用于技术机制；厂商材料可补充实现描述，但注明自述性质。通用方法论文不能冒充 DASH 采用该方法的直接证据。

保留原有有界补查和累积归档逻辑，不重新实现两轮合并。补查必须继承原查询和来源身份，不能通过重新编号导致引用错位。

### 4.5 覆盖与停止条件

三个指标必须分开：搜索执行是否成功、来源是否与 DASH 直接相关、来源能否回答技术问题。

“每个维度都有一个链接”不能直接等于技术覆盖充分。模块名称报道不等于接口实现证据；定性表扬不等于定量效果。

每个必答问题形成以下结果之一：

- 已有正文证据支持的结论。
- 部分可确认，明确具体缺项。
- 本次检索未取得直接证据，记录搜索范围与线索。
- 来源冲突，记录各方说法及处理依据。

未取得资料时可以按用户要求交付有边界的报告，但必须标记研究缺口。抓取失败、provider 故障不能被写成“官方未公开”；查不到也不能断言公开领域不存在。

停止条件继续遵循有界预算：新增查询没有带来新证据时保留缺口，不为通过指标而循环检索。

### 4.6 综合产物与模型职责

复用已有归档、背景卡片和研究充分性产物。最低需要能表达：结论、维度、所回答问题、来源正文定位、证据属性、适用边界和未决事项。

如果现有字段不能容纳技术卡片，再做最小扩展；不要建立第二套重复来源库。

代码生成与维护 ID、Hash、归档引用、去重、统计和版本；模型判断事实含义、证据支持关系、技术解释及局限。不得为了表格完整而由代码或模型补造未披露的参数。

## 5. 第二阶段：WF-4 报告写作适配

### 5.1 先修依赖与证据绑定

报告模式最小前置应为：已完成的 WF-1，加上明确选择且已完成导入审查的 WF-3B。

有用户指定模板时可额外绑定 WF-2；没有模板时不强制。原科研申请书分支的依赖保持原样。

不能简单把 WF-4 的 WF-2 要求删掉就算完成。必须同步检查：

- 普通启动的依赖解析。
- 显式前置版本校验。
- 一键重建的 lineage 与下游识别。
- ContextBuilder 的产物读取范围。
- 导出对写作版本、研究版本的追溯。

WF-4 要冻结所用 WF-3B ID 与研究产物版本；不能从“整个项目最新综合结果”隐式读取，也不能误读 WF-3 的旧研究产物。

研究结果带缺口不必一律阻止写作：明确来源、范围和已知事实后可以撰写受限结论；但没有取到必要正文或研究实际上失败时，不得宣称完成了充分调研。

### 5.2 用报告结构替代科研论证链

报告模式不要求：我方中心创新命题、研究基础、拟研发算法、消融实验、经费或研究任务闭环。

建议保留现有 WF-4 身份与分章写作机制，增加报告分支：

```text
报告提纲与问题—证据分配
  → 提纲及覆盖审查
  → 按章生成正文、表格和必要图示
  → 逐章事实/引用/表达审查
  → 全文整合与缺口检查
```

若既有 Argument Schema 强制科研节点，就为报告提纲使用小型专用契约；不要造空的 INNOVATION/TEAM_EVIDENCE 对象去满足科研 Schema，也不要用全量豁免让失效的旧链路表面通过。

提纲至少包含章节标题、该章必答问题、可用证据卡、计划图表和明确缺口。章节 ID、顺序、总字数统计等由代码处理。

### 5.3 本报告的默认结构

没有指定外部模板时，直接采用任务要求：

1. 摘要与主要发现。
2. 背景调研：对象与演进、模块与架构、流程、关键技术、效果证据。
3. 综合分析：技术特点、成熟度、局限与证据缺口。
4. 结论。
5. 参考资料、术语表与证据对照表。

原任务建议全文 6000—10000 字，背景调研约占 60%—70%。这些是建议目标，不是无依据的页数硬限制；资料不足时不要靠宏观背景凑字数。

### 5.4 技术描述、表格与图示

模块表：名称、用途、输入、输出、上下游、人员参与、实验轮次、来源、未知项。

技术表：问题、机制、对应功能/流程、公开实现证据、局限。

效果表：实验轮次、场景、对象、基线、指标、公开结果、证据属性、适用范围。

架构图/流程图只表达来源能支持的关系。分析性归纳允许存在，但必须与官方披露区分；不能把推测顺序画成已公开固定协议。

不要求图中填满每条接口和反馈路径。缺少证据时宁可标明未知，也不能从通用 AI 架构套出 DASH 的实现。

### 5.5 报告审查标准

继续保留：真实来源、引用可解析、数字与单位一致、事实不越过证据、前后不矛盾、原始声明与作者推断区分。

报告模式不启用：我方团队证据、创新闭环、研发任务—实验—指标链、申请书固定核心章节完整性。

还需检查：报告能否回答“有什么、怎么运行、用了什么技术、效果如何、哪些仍不知道”；技术章节是否真正使用了对应维度的证据，而非重复宏观背景。

这些适配同时作用于生成 Prompt、独立审查、确定性 Guard 和准备度判定，不能只改生成提示词。

## 6. WF-2 与 WF-5 的边界

### WF-2：可选模板能力

没有参考报告时跳过，结构来自用户任务。需要运行时，将其目标改为提取报告章节功能、表格/图示惯例和版式要求，不沿用“形成科研项目申请书”的固定规则。

只复用结构，不把参考报告中的结论、性能数字或机构事实转移到 DASH 报告。

第一阶段不必为此扩大改动；先让报告路径无需 WF-2 即可规划章节。

### WF-5：保留审查，兼容报告产物

继续使用既有安全检查和必要审批，不自动批准或取消门禁。重点核对是否能读取新报告章节、正确导出引用、表格和图示，是否仍错误要求申请书专属字段。

导出文件使用报告标题；不能因为内部文件名叫 proposal 就把正文改回申请书。引用列表、证据对照表、图示标注和研究缺口应在导出后仍然可见。

## 8. 分阶段验收与停止点

### A. WF-3B 适配完成后就先运行，不等 WF-4 全部改好

- SURVEY_REPORT 默认使用技术调研维度，旧申请书仍用旧八维。
- 新维度从输入到最终覆盖报告保持一致，未知维度仍被拒绝。
- WF-1 任务深度和资料截止日期进入实际模型请求。
- WF-3B 不依赖 WF-2，能够冻结正确 WF-1。
- 各技术维度有直接证据或具体检索缺口，不能用行业规模补齐模块维度。
- 搜索失败、只读摘要、转载和无关论文不冒充充分证据。
- 两轮检索结果继续合并，旧来源不丢失，引用不重编号错配。
- 持久化综合卡片、归档与缺口，供后续写作读取。

优先参考 `tests/test_wf3b_background_research.py` 中现有测试，新增报告模式正例与旧模式回归，不重写已有检索测试。

### B. WF-4 最小报告路径

- 无 WF-2、但有已完成并绑定的 WF-1/WF-3B 时可启动报告分支。
- 科研申请书原有前置和质量约束不被放宽。
- 精确绑定指定研究版本；旧 WF-3 结果或其他 WF-3B 实例不得混入。
- 不索取我方创新、团队、研发实验等不适用材料。
- 从任务结构生成报告提纲，章节使用对应证据，未知项明确保留。
- 引用错误、伪造数字或无依据升级结论仍会被拒绝。
- 重建能正确识别 WF-3B → WF-4 → WF-5 的依赖。

### C. 导出

- 实际导出可打开，标题、章节、表格、图示、参考文献和缺口标记完整。
- 安全审查仍执行，已有审批事实与版本约束保持有效。
- 输出清楚记录来源研究版本与报告版本。

测试通过不能替代真实模型验收。最终分别报告：哪些静态/回放测试通过，哪个真实工作流完成，剩余哪些阻断。不得用人工空确认或模拟产物证明全链路自动通过。
