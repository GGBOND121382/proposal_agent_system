# DASH调研任务：WF-1 Prompt与模型契约审计

核查时间：2026-09-09。检查用户提供的另一智能体修改记录、本地运行代码、数据库、真实请求、解析后的响应和原始SSE响应。此次仅做只读审计，未改动其他智能体正在修改的运行代码、服务或工作流。

## 结论

当前WF-1确实存在模型契约过重、运行时字段暴露过多、文种规则不适配和修复规范化边界混乱的问题。核心改法是将模型语义输出与持久化对象分离，而非简单删几段提示词或取消严格校验。

最新材料已清楚要求“公开资料调研与技术分析”，并明确禁止改写成科研申请书。仍发生的文种及论证结构问题不能继续归因于用户材料不够明确。

- 材料：`doc-d06185783c2e426d`，`PROJECT_BRIEF_美空军DASH系统调研分析报告.md`。数据库材料角色为 `CURRENT_PROPOSAL`。
- 最新WF-1：`wf-d3b5f338e2c2446a`。
- 核查时状态：`BLOCKED_CONTRACT`，`current_step=4`，停在 `P-PROJECT-DEFINITION-EXTRACT`。
- 该实例记录22条 `prompt_runs`，其中17条ERROR；项目定义提取调用3次、定向修复调用12次。不能把这些业务调用数等同于全部底层HTTP尝试数。

## 2. “504KB”究竟是什么

| 测量项 | 字节数 | 含义 |
| --- | ---: | --- |
| 请求归档文件 | 515,478 | 约503.4 KiB；包括排版、转义及单独存储的Schema |
| `request_size.core_request_utf8_bytes` | 239,889 | 内部登记的system、输入Envelope与Schema之和 |
| `input_envelope_utf8_bytes` | 21,289 | 实际任务上下文 |
| `system_prompt_utf8_bytes` | 117,282 | 共享规则、节点提示和内嵌Schema |
| `output_schema_utf8_bytes` | 101,318 | 展开后的模型输出Schema |
| 从system中扣除内嵌Schema | 15,964 | 剩余规则与任务说明 |

已解析system末尾的JSON，确认其与独立存储的 `output_schema` 结构相同。Schema占system正文约86.4%。输入Envelope主要由 `scheme_profile`（10,651字节）和 `source_documents`（9,454字节）构成，材料内容不是体积增长的主要原因。

**归档大小不能直接当作HTTP请求体大小。** 此次 `direct_tool_arguments=false`，使用MiniMax的 `output_json` 字符串工具包装。`app/llm.py` 会移除普通 `response_format`，工具参数仅声明一个字符串；完整业务Schema通过system提示传入。因此，不能据此断言该次HTTP请求把完整Schema发送了两份。内部 `core_request_utf8_bytes` 也不是该模式下的精确线上字节数。

元数据登记的输入token为估算值62,203，未取得服务端实际token用量。该次响应HTTP 200，结束原因为 `tool_calls`，成功解析为37,285字节的业务JSON；现有证据不支持将失败解释为上下文超限或输出截断。5.6MB的原始响应文件是22,319个SSE事件的存档，不能当作模型生成了5.6MB业务正文。

## 3. 是嵌套问题，还是字段问题

展开后Schema统计：

- 最大对象嵌套深度为5层，并非异常深的对象树。
- 102处对象Schema、845次属性定义；这是所有Schema分支中的出现次数，不是一次输出必须填845个不同字段。
- `project_definition` 子Schema为85,368字节，占输出Schema约84.3%。
- `items.items.oneOf` 同时带25种对象类型模板。
- 完整 `source_ref` 对象定义重复29次，共34,423字节，约占输出Schema34.0%。
- 当前合法引用/协议值提示的包装在14处字段中重复列出365个枚举值，使Schema增加约8,877字节。它是额外开销，但不是原有大Schema的主要来源。

因此，优先级应是减少一次调用暴露的对象类型与运行时字段、复用引用定义、按任务裁剪输入输出，其次才是调整嵌套深度。单纯压缩JSON排版主要节省存储和传输，并不消除模型需要遵守的复杂契约。

## 4. 真实响应暴露的三类问题

### 4.1 模型仍在生成代码应负责的字段

代表性原始响应包含10个项目条目和7个关系，同时生成了条目、关系和包的Hash，例如：

```text
items[0].item_hash = 000000...0001
items[1].item_hash = 000000...0002
package_hash      = 000000...0000
relations[0].relation_hash = 000000...0101
```

这些是模型填写的占位值，不是运行时计算的内容摘要。即使后续代码会重新计算，也没有必要让模型生成它们。

此次输出共有842次对象字段出现；仅对协议版本、项目/文档版本、来源元数据、状态与修复控制字段作保守统计，就有213次。除此之外还有条目ID、关系ID、Hash、锁定状态等可由运行时建立的字段。

最新阻断是模型在 `findings[3].evidence_refs` 同时写入文档ID和文档版本ID。后者属于协议命名空间，却被当作证据实体ID。另一智能体已经开始做有依据的 `docv→doc` 别名绑定，这是局部修复；更根本的措施是让模型只看到和选择一种局部证据引用。

### 4.2 调研报告被强制套入申请书规则

实际发送的共享提示要求：

- 系统目标是形成科研项目申请书。
- 围绕唯一中心命题和一至四个研究问题展开。
- 建立研究差距、局限机制、研究问题、中心命题、任务、形式化方法、实验比较和预期贡献的论证链。

这些规则没有根据本任务是技术调研报告而裁剪。输出一方面已经填写 `document_type=TECHNICAL_REPORT`，另一方面又产生 `DOCUMENT_TYPE_UNKNOWN`，要求用户进一步提供报告文种；同时产生 `ENGINEERING_OBJECTIVE_ONLY` 等科研论证问题。

这反映出任务适配和提示规则存在冲突。WF-1应明确提取“要调研什么、已有何种材料、需要什么证据与交付物”，而不应要求入场材料已经包含需要后续检索才能得到的DASH技术事实，也不应强制构造我方科研创新论证。

### 4.3 模型没有修改，运行时却报越权修改

可复现案例：`run-f5d8c735bb684166`。

对应原始修复响应：

`data/model_calls/responses/call-contract-repair-7d1f924df33341fc44e11df2-cycle-f5f5b634c5819b84-attempt-1.parsed.json`

模型返回 `decision=ESCALATE`、`changes=[]`。存档中的展开结果与 `original_object.content` 比较，差异为0。

使用该调用的真实Envelope，对输出单独执行当前 `bind_trusted_source_refs()`，可重现：

- 规范化34处来源引用。
- 在 `repaired_object` 中产生140处差异。
- 差异全部位于 `source_refs` 元数据：34处 `quoted_text`、34处 `span_start`、34处 `source_hash`、34处 `span_end`，以及4处其他来源元数据。

真实错误随后把这些路径报告为 `outside allowed_paths`、`overlaps protected_paths`、`was not declared`。

**不能将其归因于模型不遵守修复范围。** 需要区分模型语义修改与代码来源绑定。规范化应对基线与候选采用相同规则、相同可信目录，或者在扩展之前对语义补丁做权限检查，再对最终对象做独立完整性检查。不能简单放宽受保护路径，也不能让模型虚报这些代码产生的变更。

## 5. 建议的字段职责划分

| 内容 | 模型职责 | 代码职责 |
| --- | --- | --- |
| 文种、对象、任务要求 | 从自然语言识别；显式结构化用户选择直接采用 | 固定任务模式并选择相应契约 |
| 事实/要求、问题与关系含义 | 抽取、归纳、判断；保留证据选择 | 验证引用存在性、类型与闭环 |
| 引用 | 选择段落/证据局部编号；必要时选取支持语句 | 映射真实source_id、版本、类型、Hash及可定位Span |
| 对象身份 | 必要时使用调用内局部key表达关系 | 分配稳定ID，生成关系ID、版本与Hash |
| 来源等级和锁定状态 | 不生成或批准 | 从可信来源与权限规则继承 |
| 覆盖矩阵、反向引用、变更路径 | 说明语义上缺少的内容 | 根据条目、关系、引用与diff计算结构统计 |
| Finding | 说明实质缺陷、依据与涉及的业务对象 | 分配ID，映射可确定的路由和修复策略 |
| 状态、Gate、修复额度 | 提供需要人工判断的具体问题 | 综合校验及真实问题决定状态和Gate |

不能把语义判断伪装成确定性计算：某段证据是否实质支持结论、研究范围是否合理、哪些事实矛盾、某项业务缺口是否关键，仍需要模型或人工判断。代码负责身份、结构、权限和可机械验证的结果。

## 6. 推荐实施顺序

### P0：先消除规范化导致的假修复失败

为上述 `changes=[]` 案例建立回归：空语义变更不得因来源绑定产生越权报告；真正的受保护业务字段改动仍须拒绝。保留“原始模型响应→语义补丁→代码补充字段→最终校验”的独立审计记录。

### P1：给WF-1引入模型专用语义契约

当前 `SEMANTIC_PROMPTS` 已覆盖定向修复和若干WF-3节点，WF-1的安全分类、方案抽取、项目定义等主要节点尚未采用这一模式。复用已有投影/展开机制：

```text
可信完整上下文
  → 当前节点所需的短证据卡片与任务要求
  → 模型输出语义字段和局部引用
  → 代码补齐身份、来源、Hash、版本、结构统计
  → 完整持久化Schema与独立语义校验
```

模型不再承担持久化对象的全部字段；后台完整数据模型可以保留。先迁移项目定义提取和方案抽取，再迁移对应Critic，避免生产与审查两边契约不同步。

### P2：按文种和阶段裁剪职责

建立调研报告专用任务契约：重点为研究对象、问题清单、来源范围、技术深度、图表要求和效果证据要求。对没有正式申报指南的调研任务，保留真实用户任务要求，按语义区分“不适用”与“必须补充”，不要伪造指南或一律阻断。

### P3：简化模型接收的Schema及传输协议

- 只暴露当前任务需要的类型，不在每次提取中展开25种通用对象模板。
- 来源采用局部证据编号引用；完整来源对象由代码还原。
- 支持的端点优先直接结构化工具参数，避免JSON对象再序列化成 `output_json` 字符串；兼容性需实测。
- 对支持的端点使用可复用定义；不支持时，优先缩小模型Schema，不依赖无限展开公共对象。
- 共享提示按节点和文种选择，避免所有节点携带章节写作、科研创新和逐段审查要求。
- 不用增加上下文窗口和输出token上限来替代契约缩减。

## 7. 与另一智能体工作的关系

修改记录中的协议ID规范化、文档版本别名、提取覆盖由代码重建等方向是合理的，可以保留。Schema枚举提示也可以暂时减少错误，但其 `anyOf[enum, original]` 保留原字符串分支，本质上是提示而非闭合引用约束。

应把这些局部补丁纳入统一的字段所有权和规范化顺序。否则仍会继续出现“每次修好一个引用或状态错误，下一轮又在另一个协议字段阻断”的情况。

本审计未宣称某个压缩比例或新契约已经通过真实模型验证。后续验收应比较实际线上请求大小、Schema体积、重复来源字段、协议错误次数、定向修复是否零误报，以及同一DASH任务能否顺利进入应执行的调研阶段。
